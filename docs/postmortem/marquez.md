### What I built

My main role in Project 01 was working on the MangaDex integration and the features that used manga data from the API. I worked on retrieving manga information from MangaDex and helped establish the code that other parts of the application could use to access that data. I also implemented the manga search functionality and worked on the Manga Details feature so that users could search for a manga and then view additional information about it.

Another significant part of my work involved integrating features after changes from multiple branches were merged. At one point, the Search and Manga Details features were no longer accessible after other changes were merged into the project. I identified the problem and created a fix that restored the Home, Search, and Manga Details navigation while keeping the Home screen as the application's default screen.

In addition to implementing features, I created and organized several of the project's issues, tested the MangaDex API and application functionality, reviewed integration problems, and helped resolve merge-related issues. I also helped teammates troubleshoot problems when possible and contributed to some of the written and presentation work for the project.

## Biggest challenge

My biggest challenge was keeping my features working as the different parts of the application were combined. Search and Manga Details worked during development, but later merges changed shared parts of the application and caused those features to stop appearing correctly. This was difficult because the problem was not isolated to one feature or file. I had to understand how my code interacted with changes made by other members of the team, especially the application's navigation.

I handled the problem by examining the merged version of the application, identifying where the integration had broken, and creating a separate fix branch to restore the features without removing the newer Home functionality. I then tested the integrated application again before submitting the changes. This experience showed me that getting a feature working on its own branch is only part of completing it. A feature also has to continue working after it is integrated with everyone else's work.

## Most valuable thing I learned

The most valuable thing I learned from Project 01 was the importance of integration and communication in a team software project. Before this project, it was easy to think of completing a feature mainly as writing the code and making sure that feature worked. Project 01 showed me that a feature is not really finished until it works with the rest of the application.

I also learned that taking initiative can be useful to a team, but it needs to be paired with communication. My teammates specifically recognized that I caught problems such as Search and Manga Details disappearing, created many of the issues that helped organize the project, contributed a large amount of code, and helped resolve integration problems. At the same time, their feedback pointed out that I sometimes took on a large amount of work without communicating enough about what I was taking on. That is something I want to improve in my next group.

## What I carry into Project 02

### 1. Communicate what I plan to work on before taking on additional work

One piece of feedback I received was that I could communicate more with the team about the work I was taking on. I created many of the issues and contributed to several different parts of Project 01, which helped the project move forward, but it also meant that I sometimes carried a large portion of the workload. In Project 02, I want to keep taking initiative while making that work more visible to my team before I begin it.

Before taking on an additional issue or feature outside of my current responsibility, I will communicate with my team about what I want to work on and make sure responsibilities are clear.

**I will know it worked if every additional issue I take on during Project 02 has been discussed with the team and has a clearly assigned owner before I begin coding it.**

### 2. Verify requirements before beginning implementation

Another piece of feedback I received was that I should pay closer attention to assignment instructions. There was an instance during Project 01 where I misunderstood a requirement and had to redo work. I agree with this feedback because redoing work that could have been avoided costs time that could instead be spent implementing or testing the project.

For Project 02, before I begin an issue or assignment, I will compare the task against the professor's instructions and acceptance requirements. For larger tasks, I will use the issue description as a checklist while I work instead of checking the requirements only after I have finished.

**I will know it worked if I complete Project 02 without having to redo a feature or assignment because I missed a stated requirement.**

I also received feedback that I could be more outspoken about proposing ideas for the project. I agree that this is something I can improve, but I am prioritizing communication about workload and checking requirements as my two formal commitments because they are the most concrete behaviors I can measure during Project 02. I still plan to contribute ideas during planning and team discussions rather than waiting until implementation has already started.
