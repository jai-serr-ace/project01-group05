### What I built

My main role in Project 01 was working on several of the user-facing features of MangaReader. I worked on integrating the Login page, displaying manga covers, sorting manga by genre, and implementing the 18+ censorship toggle. These features were important for making the application easier to use and giving users more control over the manga content they could browse.

One of the features I worked on was integrating manga cover images into the application. Since the manga information came from MangaDex, I had to make sure the cover information from the API was correctly connected to what was displayed in the app. I also worked on genre sorting so users could browse manga based on the type of content they were interested in.

Another feature I worked on was the 18+ censorship toggle. This gave users a way to control whether adult content would be shown in the application. I also helped integrate the Login page with the rest of the application so that the different parts of the project could work together.

In addition to implementing my own features, I worked with the rest of the team to integrate changes from different branches. This required testing the application after merges and fixing problems when changes that worked individually did not work correctly once they were combined with the rest of the project.

## Biggest challenge

My biggest challenge during Project 01 was dealing with code that would work correctly on my computer and then later fail to compile when I rebuilt the project. There were times when I thought a feature was finished because the application was running correctly, but after additional changes were made or the project was rebuilt, new compilation errors would appear.

This was difficult because it was not always obvious whether the problem came from my code, another change that had been merged, or the way different parts of the project interacted. Since everyone was working on the same application, a change in one part of the project could sometimes affect code somewhere else.

I handled this by going through the errors, rebuilding and testing the application, and checking how my changes interacted with the rest of the project. When necessary, I communicated with my teammates to understand what had changed and how we could get everything working together again.

The biggest victory for me was that despite these problems, we were able to finish the project and create something usable. Seeing the different features from everyone on the team come together into one working application made the debugging and integration problems worth working through.

## Most valuable thing I learned

The most valuable thing I learned from Project 01 was that code working once does not necessarily mean a feature is completely finished. In a team project, the application needs to continue working after other branches are merged and after the entire project is rebuilt.

I also learned how important frequent testing is. Waiting too long between builds can make it much harder to determine which change caused a problem. Testing after smaller changes makes it easier to identify errors before they become mixed together with other changes.

Project 01 also gave me more experience working with GitHub in a group environment. Branches and pull requests made it possible for us to work independently, but I learned that communication is still necessary because everyone's changes eventually have to work together in the same application.

## What I carry into Project 02

### 1. Build and test the entire application more frequently

One of the biggest problems I encountered during Project 01 was having code work correctly and then discovering later that the project would no longer compile. This made debugging more difficult because several changes might have happened between the last successful build and the new error.

For Project 02, I want to test more frequently instead of assuming that a feature is finished just because it worked once. After making significant changes or merging another branch, I will rebuild the complete application and verify that the important parts still work.

This should help me identify problems closer to when they are introduced and make debugging easier for both me and my teammates.

**I will know it worked if I build and test the complete application after each major feature or merge I work on and avoid letting multiple untested changes build up before discovering a compilation problem.**

### 2. Communicate integration changes with my team

Another lesson I learned from Project 01 was that changes that seem isolated can affect other parts of the application. Since we were all developing different features, it was sometimes difficult to know whether changing a shared file would interfere with another teammate's work.

For Project 02, I want to communicate more clearly when I am modifying something that other team members may also be using. Before making a major change to shared code, I will check with the team or explain what I am changing so that everyone knows how it could affect their features.

I also want to communicate sooner when I run into a problem instead of spending too much time trying to determine whether an integration issue is only happening on my branch.

**I will know it worked if major changes I make to shared code are communicated to the team before they are merged and integration problems are discussed as soon as they are discovered.**

These are the two areas I want to focus on most during Project 02 because they directly relate to the challenges I experienced in Project 01. I still want to continue improving my Android development and GitHub skills, but testing more consistently and communicating integration changes should make my individual work easier to combine with the work of the rest of the team.
